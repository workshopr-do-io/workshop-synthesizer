# Project Retro Variant

A project retro is between a quarterly retro and a post-mortem. The project shipped (or didn't). The team wants to learn from it. The framing isn't incident-driven but it isn't routine either.

## What's different from a quarterly retro

One thing: **the "what we would have done differently" section.**

This is harder than it sounds. The synthesis lead has the benefit of hindsight; the room had to make decisions under uncertainty. The section names the choice points retrospectively without claiming the team should have known better in real time.

## The framing template

For each significant decision the team made during the project:

> *Looking back, the choice we made at [moment] was [decision]. The information available at the time supported [direction]. With what we know now, the alternative would have been [alternative]. The team isn't being graded on this — the question is whether the choice would change with the same information today.*

That phrasing is fair. It lets the team learn without indicting the past.

## What's the same as the quarterly retro

- Dissent preservation. Minority view is the data.
- Clustering with explicit minority-view extraction (Prompt #15).
- Dissent-vs-noise distinguisher (Prompt #16).
- Public write-up drafter (Prompt #17).
- Pre-send check to two voices.
- 3–7 action items, named, dated, tied to themes.

## What's the same as a post-mortem

- The cause-vs-blame discipline applies, but more gently. Project retros aren't usually about incidents, so the cause-vs-blame check (Prompt #19) isn't usually needed. If the project failed badly enough to need it, you're probably doing a post-mortem, not a project retro.

## When to use this variant

- A project shipped late or with quality issues
- A project shipped on time but didn't achieve its goals
- A project was cancelled mid-flight
- A project was successful but the team wants to extract patterns for next time

## When NOT to use this variant

- The project failed in a way that paged the team or harmed customers — that's a post-mortem
- The team didn't really run a project — it's just routine work — that's a quarterly retro
- The project is ongoing — wait until it ships or stops

## A subtle warning

The "what we would have done differently" section invites hindsight bias. Watch for:

- Sentences that imply the team should have known better
- Recommendations that retroactively privilege information that wasn't available
- Framings that make individuals look bad

The template above prevents most of this. If a section still reads as critique of the team's past judgment, rewrite using the *"with what we know now"* phrase explicitly.
